# Knee grade-3-only capacity experiment (development study)

The submitted Kassif/Singer manuscript uses one constrained knee grade (grade 3) and plots upper bounds at 40, 50, 60, 70, 80 and 90 percent of its grade-3 test count: 89, 112, 134, 156, 178 and 201. The audited Chen OAI v1 archive here has 4,130 left/right pairs, split into 5,778/826/1,656 train/validation/test images. Its untouched test portion has 223 grade-3 images, exactly the count implied by those plotted bounds. Matching counts and split sizes do not establish that image identities, preprocessing, initialization or allocations equal the published implementation. The submitted version uses EfficientNet; this study reuses frozen ImageNet ResNet18 features and trains only its linear head. It is a structural diagnostic, not paper replication.

This stage **does not access test labels or score the test split**. On the 826-image development split, derive a capacity reference solely from training prevalence: `round(826 * 757 / 5778) = 108` expected grade-3 cases. Round `0.4, 0.5, 0.6, 0.7, 0.8, 0.9` times 108 to integer caps **43, 54, 65, 76, 86, 97**. (Python's half-even rounding does not affect these six values.) These have the same nominal pressure fractions as the manuscript; absolute caps are smaller because the development population is half its test population. Grade 4 and grades 0–2 are unrestricted. Record the actual development grade-3 count only during offline scoring, never budget construction or training. Do not silently reuse these numbers on another split.

Use the already verified frozen Chen feature cache, its pinned event SHA-256, Quadro FP32 on one host, four new paired seeds 1201–1204, 20 head epochs, five CE-only warmup epochs, batch size 256, task Adam learning rate .001, and final epoch predictions without checkpoint selection. Four arms receive the identical cap at each level: ordinary Clipper, phase-matched TraLO Null, TraLO with separate constraint Adam rate .0003, and the existing PHR ALM implementation with rho .05. This ALM implementation is an exploratory comparator, not the Kassif/Singer loss. Null has no constraint updates but shares the TraLO phase reset; Clipper lacks the reset. The TraLO constraint controller retains initial lambda .01, lambda increment .05 and rho .5. No auxiliary sample-aware term. The single-cap change tests whether previously coupled grade-3/grade-4 pressure hid a consistent effect; the expected signature is reproducible positive TraLO-minus-Null **allocated grade-3 F1** without degradation in overall accuracy or feasibility. Failure is no repeatable improvement across caps and seeds, or a gain restricted to one post-hoc-selected cap.

For each cap report grade-3 F1, precision, recall, TP/FP/FN, overall accuracy and macro-F1 on raw predictions and on both `upper_bound_correction` and `capped_first` allocations. The manuscript's predict-then-optimize allocation is not confirmed identical to either local policy. The primary within-cap contrast is TraLO minus Null for capped-first grade-3 F1; ALM minus the same Null and TraLO versus Clipper are secondary. Show every paired seed, mean, SD and t interval; adjust any across-cap positive discovery claim for the six prespecified cap comparisons. Also report raw hard and soft counts, quota violations, actual applied/skipped task and constraint updates, runtime and source/data/config hashes. No favorable-only cap or epoch selection. The test split remains reserved for a fixed later confirmation, not this development campaign.

Stage gate: run 1201 at cap 43 first; verify all four arms, finite loss/gradients, exact shared warmup and batch hashes, expected dose, final artifact hashes, independently recomputed metrics and both allocator quotas. The gate depends on integrity, **not score**. Then run the other 23 cap/seed combinations. Preserve failures, launch receipts and every result. Inspect GPU UUID, process owner and free memory on **both** DSI hosts immediately before dispatch; do not share or preempt another user's GPU. Never relaunch an ambiguous or already active run. Any code change requires tests, GitHub and DSI pushes, a new immutable release and remote byte/test parity before execution.

After this stage, evaluate whether a training-only, full-backbone constraint phase is warranted. Frozen-feature head results cannot answer whether shaping the representation helps. That experiment needs a separate preregistered, matched computational budget; do not infer a new winner from this stage or simply sweep strengths until favorable.
